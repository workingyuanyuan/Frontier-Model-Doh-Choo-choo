The two sibling rows drifted the same way but stayed inside tolerance and are therefore
scored MATCH — worth knowing they are not exact either:

- GPT-5.6 Luna (low): scraped `0.3279`, source `0.327815` (Δ 0.0085 pp; `last_updated`

## 4. Other observations

### 4.1 Locators that do not describe where the value actually is

1. **`briefcase_breakdown.rubric` (rows 1–3).** That path resolves to an _object_, not a
   number. The scraped value is at `briefcase_breakdown.rubric.pass_rate`. The locator should
   say `.rubric.pass_rate`. (Values themselves are correct.)
2. **Field-name casing does not match the page (rows 10–12, 49–54).** The locators are written
   in `snake_case` (`apex_agents`, `tau_banking`, `terminalbench_v2_1`), but on
   `/models/*` pages and on most `/evaluations/*` pages the RSC payload uses `camelCase`
   (`apexAgents`, `tauBanking`, `terminalbenchV21`). Only three of the pages sampled
   (`aa-briefcase`, `omniscience`, `gdpval-aa`) embed the additional `snake_case`
   `defaultData` object the locators appear to assume. A human following these locators
   literally will get "field not present" on 9 of the 30 AA rows. The values are all there and
   all correct once you allow both spellings, but the locator format is misleading and is a
   trap for whatever code re-resolves it later.
3. **LiveBench locators do not name their columns (rows 34–45).** `"averaged over IF task
columns"` is not independently checkable. The column sets I had to reverse-engineer (and
   which reproduce every one of the 12 scraped values exactly) are:
   - instruction-following: `paraphrase`, `simplify`, `story_generation`, `summarize`
   - language: `connections`, `plot_unscrambling`, `typos`
   - mathematics: `AMPS_Hard`, `integrals_with_game`, `math_comp`, `olympiad`
   - reasoning: `logic_with_navigation`, `spatial`, `theory_of_mind`, `zebra_puzzle`

   Note `consecutive_events` is present in the CSV but is in none of the four groups. That may
   be deliberate, but it is invisible in the locator and should be written down explicitly.

### 4.2 Unit / scale inconsistency in the sample itself

Every row carries `"unit": "percent"`, but the stored `rawScore` is on two different scales:

- AA rows and Frontier Code rows: `rawScore` is a **fraction 0–1**, and `normalized = raw × 100`.
- LiveBench rows and DeepSWE rows: `rawScore` is already **0–100**, and `normalized = raw`.

For DeepSWE this is an outright unit conversion against the source: the source
`pass_rate` is a fraction (e.g. `0.686046511627907`) and the pipeline stores `68.6046511627907`.
Correct arithmetic, but `unit: "percent"` describing both `0.5273` and `68.60` means the field
carries no information and cannot be used to validate scale.

### 4.3 Effort labels that do not match the source's own effort buckets

- **Row 21, MiniMax M3 (`frontier-code-1-1`).** Sample `effort` is `"max"`, but the locator
  reads the `"none"` bucket, and `data.json`'s `efforts` map lists MiniMax M3 as having only
  `["none"]`. The locator is right and the value is right; the `effort: "max"` label is a
  pipeline-side default that misrepresents the source.
- **Rows 50 and 53, "GPT-5.6 Luna (Non-reasoning)".** Sample `effort` is `"max"` for a model
  variant the source explicitly labels non-reasoning. Same pattern as above.
- **Row 11, "GPT-5.6 Luna (max)".** The AA slug is bare `gpt-5-6-luna` with no `-max` suffix,
  while sibling variants use `gpt-5-6-luna-low` / `-high` / `-non-reasoning`. That is a source
  quirk, correctly handled, but it is the kind of thing that breaks a naive slug builder.
- Frontier Code also has an `Inkling` entry whose effort bucket is the string `"0.99"`. Not in
  the sample, but it will break any enum-typed effort field.

### 4.4 Model names

Every AA row's `model` string is byte-identical to the `name` field on the source page,
including the long Claude Fable 5 string. DeepSWE, LiveBench and Frontier Code rows use each
source's own key format (`claude-fable-5`, `claude-fable-5-max-effort`, `Claude Fable 5`
respectively), which is correct per source but means three different identifiers for one model.
No renames or drift found.

### 4.5 Sources updated since `retrievedAt`

- **AA GDPval** — updated seconds to hours after the scrape; see §3.
- **DeepSWE** — `generated_at` is `2026-08-13T16:11:55Z`, i.e. the artifact has been
  regenerated since `retrievedAt` (2026-08-12T16:44:09Z). All three sampled `pass_rate` values
  are nevertheless unchanged.
- **LiveBench** — `table_2026_06_25.csv` is byte-identical with and without the `?v=` cache
  buster, so the release itself is stable. I could not confirm from `livebench.ai` (the
  homepage is a JS shell with no table manifest) whether a **newer** release file exists; a
  human should check that separately, since a stale-but-correct release is invisible to this
  kind of value-level audit.
- **Frontier Code** — `data.json` carries no timestamp at all, so freshness is unverifiable
  from the artifact.

### 4.6 A benchmark whose headline metric is not the one being scraped

On the AA payload, the top-level `omniscience` field for Claude Fable 5 is `43.3` — the
Omniscience _Index_, on a different scale — while `aa-omniscience` scrapes
`omniscience_breakdown.total.accuracy` (`0.6535`). Both are legitimate, and the locator is
explicit about which one it takes, but anyone eyeballing the AA page will see 43.3 and think
the pipeline is wrong. Same shape for `gdpval` (`1737.71`, an Elo) vs `gdpval_normalized`
(`0.618855`), and for `briefcaseElo` (`1574.47`) vs the rubric pass rate (`0.5596`). Worth a
line in the methodology doc.

## 5. Notes for the human spot-check

**Straightforward:**

- **LiveBench** — a 43-row plain CSV, 7 KB. Open it, average four named columns, done. The
  only friction is that the locator doesn't tell you which columns; use the lists in §4.1.
- **DeepSWE** — flat JSON, `rows[]` keyed by `config`. One `jq` expression per row. Remember
  the ×100.
- **Frontier Code** — the static export at
  `https://cognition.com/data/frontiercode-leaderboard/data.json` is exactly the shape the
  locator describes (`v1_1.data[model][effort].main.new_score`). The rendered
  `cognition.com/frontiercode` page is a JS app, so go straight to the JSON.

**Awkward:**

- **Artificial Analysis** — these are the ones to budget time for. The `/evaluations/*` pages
  are 0.6–10.5 MB of HTML, and `aa-briefcase` and `omniscience` are over 10 MB, which will
  hang a browser's view-source. The numbers live in the escaped RSC payload; you must
  unescape `\"` → `"` before searching, then brace-match outward from `"slug":"<slug>"` to get
  a parseable object.
- The same page can contain **two** objects for one slug: a small 6-key stub (nav/link data,
  no scores) and the real 50–133-key model record. Grabbing the first hit gives you the stub.
- **Key casing varies by page** (§4.1 item 2) — always try both spellings.
- If spot-checking visually instead: the GDPval mismatch in §3 is **not** visible on the
  rendered chart. Both `0.618855` and the scraped `0.61943` display as `61.9`. You have to
  read the payload (or the Elo, `1737.71` now vs `1738.86` implied) to see it.
- `"$undefined"` appears in these payloads (e.g. `host_models`) and means missing data; none of
  the 54 sampled fields resolved to it.
