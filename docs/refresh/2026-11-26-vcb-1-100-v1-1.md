### 證據庫事故（已修復）

第一次重新匯入時，這個 worktree 的證據庫是以 hard link 指向主 checkout 的 `artifacts/evidence/store.sqlite`。但 SQLite 的 WAL 與 shm 檔是各目錄各自一份，兩邊同時寫入無法協調。15:55 左右，本 worktree 與在主 checkout 匯入 AA 的另一個 session 同時寫入，資料庫因而損壞（"database disk image is malformed"）。

- 另一個 session 從損壞檔中救出可讀的列，重建證據庫，`pnpm evidence verify --full` 通過。遺失的是今天 267 筆 capture 紀錄與 1 個 snapshot（包含本 session 的模擬匯入）。損壞原檔保存在主 checkout 的 `artifacts/research/2026-11-26-evidence-repair/`。
- 本 worktree 把舊的 hard link 移到 `artifacts/research/2026-11-26-evidence-repair-worktree/`，改用 `VACUUM INTO` 從修好的證據庫建立獨立副本（`quick_check` 為 ok），再以 `pnpm evidence init` 登記本 checkout 的快照。
- `init` 回報 144 個原檔在本 worktree 缺少（主 checkout 今天新擷取的）。原檔以內容雜湊命名、不會被改寫，所以從主 checkout 以 hard link 補上；證據庫本身不再共用。
- 之後才重新匯入並跑 release；release 的 `evidence` 步驟通過完整檢查。

## 1-100 v1.1 的評估

Vals 頁面（[vcb-1-100-v1-1](https://www.vals.ai/benchmarks/vcb-1-100-v1-1)，更新日期 2026-11-18，`dataset_type: private`）說明：

- 每題從一個完整通過的 Vibe Code Bench v1.1 應用程式開始，依序處理最多十個前後相依的產品需求。需求以一般用語描述，程式碼與對話全程保留。
- 每一輪由瀏覽器代理執行新功能流程與挑選的回歸流程。失敗判定再由第二位評審（Claude Sonnet 5.5）依錄製證據複核，確認有實作問題才算失敗；複核無法定論時，依 Vals 政策算通過。
- 分數是從第一輪起連續通過的輪數除以計畫輪數，在 50 題測試集上取平均。驗證集另外分開，不混入分數。
- 所有模型使用同一個修改過的 OpenHands V1 環境，每題共用十小時建置時間。
- v1 頁面標示「Archived Benchmark」，並寫「Vibe Code Bench 1-100 v1 has been superseded by v1.1, which updates the prompts, workflows, and failure-review policy.」

它和 Vibe Code Bench v1.1.1 不重複：v1.1.1 測從規格建出應用程式，1-100 測在既有應用程式上持續改動而不破壞原有功能。兩邊都有、檔位相同的 7 個模型，排名的 Spearman 相關約 0.79；但 1-100 的分數分布寬得多，前段模型在 v1.1.1 差距不到 4 分，在 1-100 是 31～55 分。

### Claude Opus 5.5 那一列

頁面寫明：「Only Claude Opus 5.5 used fallbacks: 12 of 50 tasks, 16 fallback events, with Claude Opus 4.8 or Claude Opus 5 taking over the request. … Opus 5.5's published score includes this fallback work; capped at the last iteration completed before each task's first fallback, its score is 23.55%.」

公布的 30.95 包含其他模型的工作，不能完整算在 Opus 5.5 身上；23.55 只出現在說明文字中，不是榜單欄位。使用者決定這一列不計分。這一列仍物化為 `EXCLUDED` 證據，並附上原因。
